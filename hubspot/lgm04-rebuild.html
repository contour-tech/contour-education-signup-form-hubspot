LGM-04 Rebuild

The 82-action waitlist workflow, rebuilt as two workflows of nine and fourteen actions. Every custom code action is written. This describes what the system does, path by path.

Built and off · merge service and student ID issuer deployed · ID counter seeded at 158000

One constraint shapes everything

HubSpot unenrols a contact from every active workflow the moment it is merged. A run cannot merge halfway and carry on.

The old workflow worked around this by merging in its very last action, which meant carrying two record IDs — a temporary form contact and a canonical one — through the whole run, plus a recovery path for every place they diverged. That bookkeeping was roughly half its complexity: five copies of the merge script, a student_id fallback that read from the temp record and deliberately declined to write it back, and a fifth outcome branch that existed only to route around an email send that would have gone to the wrong record.

So A merges and dies. B does the work on the one surviving record. Everything downstream gets to assume the enrolled contact is the student — the assumption the old workflow could never make.

The handover

Separate workflows cannot share action outputs. Three contact properties carry everything across the gap.

Why A's first two actions are property clears

Any property write re-evaluates B's enrolment trigger. Without the clear, writing the identity blob two actions later could enrol the record in B before the merge — and the merge would then unenrol it mid-run, leaving a half-written student with no trials and no email.

Workflow A — resolve, then merge

Nine actions. Decides who this person is, sends the SMS, merges any duplicate, and hands over.

Reading the three decisions

How it decides which fields are the student's

The form has two field groups — generic and dedicated. Identity resolution decides which is which by name presence, never phone. The old version accepted a phone as evidence, and since the student upsert writes student_phone_number on every run, a resubmission left that value sitting there — so the check read stale data as "dedicated student data present" and pulled in a student with a phone and no name, while the real name sat unread in the generic fields.

Workflow B — do the work

Fourteen actions on one record. Sync, school, trials, comms, finish — with every failure landing somewhere a person will see it.

What each stage actually does

1
Student and guardian sync
Writes the student. Then finds or creates the guardian, associates them, and points parent_email at whoever is actually primary. If the guardian's email matches a Student-typed record it changes nothing about that record — the old version patched contact_type: "Parent" onto whatever it matched, so a parent typing their child's old address converted that student into a parent and overwrote their name.
2
Branch — which half broke?
setupNo identity blob. Nothing can be inferred safely. Stop.
studentThe write was rejected. Nothing downstream is safe. Stop.
guardianCarry on. The student is already saved; a guardian clash must not cost them their trial and their email.
unknownUnclassified error. Stop, and say the state is unknown.
3
School verification
Matches the ACARA ID to a school, marks it current, demotes the previous one to past. Recognises the sentinels the form actually sends — HubSpot ships this form with acara_id defaulted to "1", which the old version searched for as a real ID. Separates "never asked" (overseas, UK, NZ — the field is not shown) from "asked and unmatched".
13
Create trials
One Trial per subject. Asks the ID issuer for a student_id if the record has none — no polling. Each subject is processed independently, so one unrecognised code cannot cost the student their other four. A Trial that is created but cannot be associated is deleted again, because a Trial attached to nothing is invisible in the UI forever.
22
Build comms
Renders the student's HTML and the guardian's, writes both records, and sets the trigger flag for that outcome — in the same write as the content, so a record is never flagged for sending with a half-written body. Five actions in the old workflow; one here.
34
Finish
Clears all three handover properties. It refuses to clear when the blob on the record is newer than the one processed — that means a second submission landed mid-run, HubSpot would not enrol the contact twice, and clearing would discard it silently. It leaves everything alone and raises a task instead.

Why the flags survived the rebuild

Every one of those trigger properties existed for a single reason, stated outright in the old action's own header: the enrolled contact might not be the student, so a native send would mail an often email-less temporary record. Merge-first removes that reason entirely — and one leg, send_first_time_confirmation_mail, went with it.

The rest stayed because the email templates live in four separate sending workflows, which also set marketing contact status and clear their own flags. Collapsing those into this workflow is a real simplification, but it is a different piece of work from changing the architecture, and doing both at once would make a regression impossible to attribute.

Set marketing contact status is not optional

These are marketing emails. HubSpot drops marketing sends to non-marketable contacts with no error, no branch and no trace — the workflow reports success. Around 83% of the Student, Parent and Guardian contacts in this portal came from a bulk import, which is exactly the population most likely to be non-marketable.

Outside the workflows

Three services the workflows call, and four they hand off to.

Merge service deployed

One implementation behind one endpoint, rather than five copies of a script in five actions. It is the only irreversible code in the system, which makes it the code most worth testing — and a Cloud Function can be tested where a HubSpot custom code action cannot.

Idempotent: if the records are already merged it reports success rather than writing a second note and a second audit row, so a HubSpot retry is safe. It captures the absorbed record before the merge, because afterwards that record is unreadable and the capture is the only surviving evidence of what was destroyed.

Student ID issuer deployed

The old generator ran two HubSpot searches and a patch against an eventually consistent index: read the highest existing ID, add one, search again to check nobody had taken it. An ID written seconds earlier may not be indexed, so both reads can miss it and two signups can be handed the same number — most likely on a busy day. Around it sat a five-attempt collision loop and four workflow actions of polling.

A Firestore transaction on one counter is atomic and strongly consistent. Verified against 6,105 live records: the sequence is global, not per surname.

PAR157115  Park          13:45
PAR157114  Park          13:43
BAJ157113  Bajwa         12:41
FAH157112  Fahim         12:24
AL-157110  Al-Shishachi  11:47   ← the old prefix rule

The prefix now takes the first three letters of the surname. The old rule took the first three characters, which produced AL-157110 and — on a surname of "A Kumar" — A K157097, an identifier with a space in it that does not survive a CSV round-trip or a URL.

Twenty simultaneous callers were tested: twenty distinct numbers, no gaps. The counter is seeded at 158000, deliberately clear of the highest live ID, so anything above it is unmistakably ours.

Four sending workflows existing

They own the email templates, set marketing contact status before each send, and clear their own trigger flag on the way out — which is what makes each flag a one-shot and lets a second signup re-trigger correctly.

Known gaps

Five things that are not finished. All of them are visible rather than silent, which is the point.

  • supabase_id is never written by anything we control. The Trial's own student_id field holds it, so Trials get a blank one. The old workflow polled for it through three retry tiers and then created the Trial with a blank one anyway — so blank ones already ship. Needs the student-accounts team.
  • already_enrolled has never been written to a single contact — not true, not false, no value at all, against 6,112 contacts carrying a student ID. So that outcome has never fired. The intent is worth keeping: do not tell a paying student their waitlist spot is confirmed. It is simply not implemented, and nothing in HubSpot carries the signal.
  • Association type 994 is unexplained. The live action links Trials to Courses with it and demonstrably works, but the portal's own association schema reports nothing between those two objects in either direction. That one call is now non-fatal and reports itself, so if it is dead we will see it named rather than watch every subject fail.
  • The old ID generator is still running. Two things issuing into a unique property will collide eventually. We are 884 numbers clear.
  • Workflow A still triggers on the test property. Swap it before go-live.
